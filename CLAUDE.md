# Scholz Kitchen

Personal kitchen, meal-planning, and grocery PWA for a two-person household. One real user (Dan) on an iPhone home-screen web app; the second person (Brigitte) is a **persona with her own profile and ratings, not a login**.

Hard constraint: **$0/month to run.** Every design choice below follows from that.

## Architecture (non-negotiable)

| Layer | Choice | Notes |
|---|---|---|
| Frontend | PWA: plain HTML/CSS/JS ES modules, **no build step, no framework** | Mobile-first, one-handed iPhone use. Manifest + service worker; installable; Shopping works offline. |
| Hosting | GitHub Pages from this **public** repo | **No personal data in the repo, ever.** `seed/` is gitignored. Never hardcode the Apps Script URL or token. |
| Database | Private Google Sheet, one tab per table | All household data lives only here (plus the phone's local cache). |
| API | Google Apps Script web app bound to the Sheet (`apps-script/Code.gs`) | `doGet` reads, `doPost` writes. Shared secret token in Script Properties (`TOKEN`). POSTs are sent as `text/plain` to avoid CORS preflight. |
| AI | **None from the app.** | Receipts, weekly planning, store ads happen in Claude chat on the existing subscription. Chat produces Import JSON (below); the app validates, previews, and writes it. |

### Data flow

- On boot the app renders from the local cache immediately, then pulls all tables (`GET ?action=read`) in the background.
- Every edit is applied locally first, then queued in an **outbox** (localStorage) and flushed to `POST {action:"upsert"|"delete"}`. Offline edits (e.g. checking items in the store) flush when back online. After a pull, pending outbox ops are re-applied on top of server data so nothing is lost.
- Conflict policy: last write wins per row. Server stamps `updated_at`.
- All cells in the Sheet are stored as plain text (`@` number format) so Sheets never auto-converts dates. The API casts number columns on read and JSON-encodes/decodes JSON columns.

### API contract (Apps Script)

Everything is a `POST` with a `text/plain` JSON body containing `token`, so the token never appears in a URL. `GET` only returns a hello (no data).
- `{"token":T,"action":"ping"}` -> `{ok:true, version, tables:[...]}`
- `{"token":T,"action":"read","tables":["A","B"]}` (omit tables = all) -> `{ok:true, data:{Table:[rows]}, server_time}`
- `{"token":T,"action":"upsert","table":"X","rows":[...]}` -> partial merge by `id`; unknown id = insert
- `{"token":T,"action":"delete","table":"X","ids":[...]}`
- `{"token":T,"action":"batch","ops":[{action,table,rows|ids},...]}` -> applied in order (the outbox uses this)
- `{"token":T,"action":"setup"}` -> creates missing tabs/columns (never deletes)
- Errors: `{ok:false, error:"..."}` (always HTTP 200, Apps Script limitation)

## Data model

Every table's first column is `id` (string) and last column is `updated_at` (ISO, set by server). `WeekPlan.id` is the date (`YYYY-MM-DD`). `ShelfLife.id` is the keyword slug. Other ids are `<prefix>_<random>` from the app or stable ids from Import JSON.

Columns (in Sheet order). `[n]` = number, `[j]` = JSON, everything else is text. yes/no fields are the literal strings `yes` / `no`.

- **Inventory**: id, name, category (protein/produce/dairy/pantry/spice/frozen/condiment/other), location (fridge/freezer/pantry/spice rack/counter), tracking (exact/coarse), qty[n], unit, level (have/low/out; coarse only), purchased_date, store, opened, opened_date, expires_date, expires_source (printed/estimated/manual), status (active/used/tossed), notes, confidence, source, updated_at
  - Blank `level` AND blank `qty` on a non-confirmed row = **stock unknown** (typical for imports). Planning must not treat it as on hand.
- **ShelfLife**: id, keyword, category, pantry_days[n], fridge_unopened_days[n], fridge_opened_days[n], freezer_days[n], notes, updated_at. Seeded from USDA FoodKeeper (Phase 2). Unprinted dates are estimated from this; marking opened recalculates with `fridge_opened_days`. Manual override always wins.
- **Tools**: id, name, category (cookware/bakeware/appliance/utensil/knife/other), notes, confidence, source, updated_at
- **People**: id, person (Dan/Brigitte), item, type (hard_no/soft_no/favorite), notes, confidence, source, updated_at
- **Recipes**: id, name, source_type (url/youtube/book/ai/own), source_ref, ingredients[j], tools_needed[j], cuisine, effort (low_energy/normal/project), active_minutes[n], leftover_friendly, servings[n], tags[j], my_notes, status (idea/active/less_often/retired), confidence, source, updated_at
  - `ingredients`: `[{"name":"shrimp","qty":300,"unit":"g"}, {"name":"baby potatoes","qty":400,"qty_max":500,"unit":"g"}, {"name":"garlic","qty":null,"unit":""}, {"name":"honey","qty":7,"unit":"g","note":"orig: 1 tsp","optional":true}]`
  - `qty: null` = unknown amount (never guess). Ranges use `qty` (low) + `qty_max` (high).
  - `servings` is the base yield used for event scaling; blank = assume 2.
  - Book recipes store page ref + our own ingredient list and notes, never the book's text.
  - `tools_needed`, `tags`: JSON string arrays. Tag the main protein (e.g. `"shrimp"`) to support variety rules.
- **Ratings**: id, recipe_id, date, person, stars[n] (1-5), make_again (yes/maybe/no), notes, updated_at
- **WeekPlan**: id (=date), week_start, date, who_home (both/dan/brigitte/none), cooking (yes/no/out), recipe_id, backup_recipe_id, notes, updated_at
- **Events**: id, date, headcount[n], menu_ideas, guest_notes, recipe_ids[j], updated_at
- **ShoppingList**: id, item, qty[n], unit, store (Aldi / Pick 'n Save / Karl's Country Market / Woodman's / Kwik Trip / Piggly Wiggly / Fresh Thyme / other), section (produce/meat/dairy/bakery/frozen/pantry/household), reason (recipe id, `restock`, or `event:<id>`), on_sale, sale_price[n], checked, notes, updated_at
- **Gaps**: id, item, type (tool/spice/ingredient), recipe_id, date, swap_used, updated_at

Additions beyond the original brief (keep them): `id`/`updated_at` everywhere, `notes` on Inventory/ShelfLife/ShoppingList, `servings` on Recipes.

### Confidence & source

People, Recipes, Tools, Inventory carry `confidence` (confirmed/likely/unsure) and `source` (chatgpt_import/manual/receipt/chat).
- Planning may use likely/unsure as a nudge; **confirmed always wins on conflict**.
- An unsure dislike is treated as **soft_no** until confirmed.
- Manual entries in the app default to `confirmed` / `manual`.
- The Review screen is the queue of every non-confirmed row.

### Recipe status and rotation

- `idea` = discussed/planned, never confirmed cooked. Becomes `active` the first time it is rated.
- Rotation (Phase 2): average each person's stars separately. If either person gives 1 or 2 stars **twice**, -> `less_often`. A `make_again: no` from either person -> `retired` (undoable).
- Planning can suggest ideas but leans on active recipes.

### Units

Metric first. Weights in **g**, volumes in **ml**, whole items as counts (`ea`, or a count word like `clove`, `can`). Convert lb/oz/kg on import. Cups/tbsp/tsp use **ingredient-specific** densities (`js/units.js`), never a generic number; keep the original in `note`/`notes` (e.g. `orig: 1 cup`). Unknown density -> keep ml and say so.

### Store routing (default, editable in Settings)

meat -> Karl's Country Market; staples (pantry, dairy, bakery) -> Aldi; everything else (produce, frozen, household) -> Pick 'n Save. A sale (`on_sale: yes` with a store) overrides routing.

## Import JSON format (chat <-> app contract)

Claude chat emits exactly this; the Import screen validates, previews, and writes it.

```json
{
  "format": "scholz-kitchen-import",
  "version": 1,
  "kind": "seed | receipt | weekplan | sale_ads | event | ratings | general",
  "source": "chat",
  "note": "One line shown in the preview",
  "tables": {
    "Inventory":    [ { "name": "ground beef", "category": "protein", "location": "fridge", "tracking": "exact", "qty": 680, "unit": "g", "purchased_date": "2026-10-25", "store": "Karl's Country Market" } ],
    "ShoppingList": [ { "item": "lemons", "qty": 2, "unit": "ea", "section": "produce" } ]
  },
  "delete": { "ShoppingList": ["shop_abc123"] }
}
```

Rules:
- Table and column names exactly as in the data model. Unknown columns are dropped with a warning. Enum values must match (case-insensitive accepted, normalised to the canonical spelling).
- Row **with** `id` = upsert (only the given fields change). Row **without** `id` = insert with a generated id. Use stable ids when re-sending the same data (re-importing must not duplicate).
- Top-level `source` fills rows' `source` where the table has one and the row lacks it. Rows from chat default to confidence `likely` unless Dan confirmed them in the conversation.
- Quantities: grams/ml/counts. The importer converts `lb`, `oz`, `kg`, `fl oz`, `cup`, `tbsp`, `tsp` and records the original in notes, but chat should send metric already.
- Dates `YYYY-MM-DD`. JSON columns (`ingredients`, `tools_needed`, `tags`, `recipe_ids`) are real JSON arrays, not strings.
- `ShoppingList` rows without `store` are routed by section. `checked` defaults to `no`.
- `WeekPlan` rows use `"id": "<date>"`.
- Receipt imports: one Inventory row per purchased item, `source: receipt`, `confidence: confirmed`, store + purchased_date filled, weights converted to g. No `expires_date` -> app estimates from ShelfLife (`expires_source: estimated`).

## Planning rules (the app and chat both follow these)

- All recipe ingredients in grams when possible (ml for liquids, counts for whole items).
- 5-6 home-cooked dinners a week, more on weeknights than weekends.
- Variety night to night: don't repeat a protein or cuisine on back-to-back nights.
- Prioritise items expiring soonest.
- Never use a hard_no for **either** person. Flag soft_nos (fine if minor/hidden). Unsure dislikes = soft_no. Never infer one person's preferences from the other's.
- Leftovers only for recipes marked `leftover_friendly: yes`.
- Every planned night gets a `backup_recipe_id`: low_energy (about 15 min, pantry-only, minimal cleanup) using what is already on hand.
- If a recipe needs a tool or spice we don't own, log it in Gaps and suggest a swap.
- Only `confirmed`/`likely` stock with a known level/qty counts as on hand. Recipe ingredients and recipe equipment never imply stock or ownership.

## Screens

1. **Tonight** (home, Phase 2): tonight's dinner, big "Low energy tonight" swap to backup, Expiring soon (3 days; use/toss/replace colours).
2. **Week** (Phase 2): 7-day plan, who's home, cooking/out, swap meals.
3. **Shopping**: grouped by store then section, big tap targets, offline.
4. **Kitchen**: inventory by location; +/- for exact, tap-cycle have/low/out for coarse; opened/used/tossed. Tools and spices here too.
5. **Recipes**: search + filters (effort, cuisine, leftover friendly, status); detail with source link, ratings, conflict flags.
6. **Rate** (Phase 2): day after a planned meal; Dan first, then "Ask Brigitte" card.
7. **Events** (Phase 2): "X people Saturday, thinking Y"; attach recipes; scales shopping list by headcount / servings.
8. **Import**: paste or load JSON, validate, preview, write.
9. **Settings**: Apps Script URL, token, store routing, sync, backup export.
10. **Review**: one card at a time, Confirm/Edit/Delete, filter by section.

## Phase plan

- **Phase 1** (built): Sheet template + Apps Script API, installable PWA shell, Kitchen, Recipes, Shopping, Import, Review, Settings. Seed generated from `seed/chatgpt_export*.md` into `seed/*.json` (load via Import).
- **Phase 2**: Tonight + low-energy swap, Week, Rate with Brigitte persona, rotation logic, ShelfLife estimates (FoodKeeper seed), Events with scaling, Gaps.
- **Phase 3**: polish, offline reliability, lessons from real use.

Stop after each phase so Dan can test on the phone.

## Conventions

- Keep `js/schema.js` and `SCHEMA` in `apps-script/Code.gs` identical. Adding a column: add it in both, redeploy the script, run Settings > "Set up Sheet" (adds missing columns, never deletes).
- After changing any shell file, bump `CACHE_VERSION` in `sw.js` so phones pick up the update.
- No external CDNs (offline + privacy). No analytics.
- Seed migration safeguards (from the ChatGPT export): discussion != cooked; planned != liked; recipe ingredient != stock; recipe equipment != owned; catering != homemade recipe; never invent amounts, links, ratings, or outcomes.
- Test locally: `node tools/serve.mjs` (static server on :8080) and `node tools/mock-api.mjs` (runs the real `Code.gs` against an in-memory fake Sheet on :8787). See `tools/README.md`.
